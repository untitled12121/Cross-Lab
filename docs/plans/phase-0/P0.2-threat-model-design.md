# P0.2 Threat Model and Trust Boundaries — Design

**Status:** Proposed for review  
**Phase:** Phase 0 — Architecture and Security Specification  
**Milestone:** P0.2 — Threat Model and Trust Boundaries  
**Architecture baseline:** `docs/architecture/MASTER-ARCHITECTURE.md`, Revision 2.0

## Purpose

P0.2 defines the security model that later identity, trust, policy, protocol, session, platform, recovery, update, and privileged-service work must satisfy. It turns the Master Architecture's security invariants into explicit trust boundaries, attacker assumptions, protected assets, required controls, and testable security properties.

This milestone does not select concrete cryptographic message formats, pairing transcripts, wire serialization, or platform-specific privilege mechanisms. Those decisions depend on this threat model and belong to later Phase 0 specifications.

## Scope strategy

Cross-Lab will use a **foundation-first threat model**.

The model covers the trust boundaries inherited by every Cross-Lab capability:

- owner and device identity boundaries;
- untrusted network and transport boundaries;
- authentication, trust, and policy separation;
- control-plane authorization and data-plane binding;
- network-facing agent and platform-adapter boundaries;
- privileged-service isolation and local IPC;
- recovery authority separation;
- optional relay/hub distrust assumptions;
- update trust at the architectural level;
- audit, privacy, denial-of-service, replay, downgrade, and compromised-peer considerations.

Future feature families such as media capture, remote desktop, plugins, device login, distributed compute, and individual platform integrations will extend this foundation with focused threat analyses when their implementation begins.

## Alternatives considered

### Whole-project exhaustive threat model

Model every planned feature and platform during Phase 0.

This provides broad coverage but would be dominated by speculative platform behavior and future capabilities that have not yet been designed. It would create a large document that becomes stale before implementation.

### Phase-1-only simulator threat model

Model only the identity, pairing, policy, protocol, and session behavior needed by the Core Simulator.

This is smaller but omits privilege, recovery, relay, and update boundaries that directly constrain early domain design.

### Foundation-first model — selected

Model the architectural security boundaries that all later features inherit, while explicitly deferring feature-specific detail.

This is the smallest model that prevents early security decisions from making later least-privilege, recovery, or remote-connectivity requirements impossible.

## Deliverables

P0.2 will produce three durable documents:

```text
security/THREAT-MODEL.md
docs/architecture/SECURITY-BOUNDARIES.md
docs/plans/phase-0/P0.2-threat-model-implementation.md
```

`security/THREAT-MODEL.md` is the security-analysis document. It records assets, actors, attacker capabilities, threats, mitigations, assumptions, residual risks, and security properties.

`docs/architecture/SECURITY-BOUNDARIES.md` is the concise normative boundary reference for developers. It defines which components may trust which inputs and which validations must occur before authority crosses a boundary.

The implementation plan decomposes the documentation work into independently reviewable checkpoints and defines verification against the Master Architecture.

## Security assets

The threat model will explicitly protect at least the following asset classes:

### Authority assets

- owner root authority;
- device signing authority;
- recovery authority;
- administrative authority;
- device private keys and hardware-backed credentials;
- update signing roles and trusted metadata roots.

### Authorization assets

- trust records and revocation state;
- capability declarations;
- policy rules and decisions;
- authorization obligations and constraints;
- authorized operation identifiers and session bindings.

### Protocol/session assets

- authenticated peer identity;
- protocol-version negotiation;
- session freshness and channel binding;
- control-plane integrity;
- data-stream authorization bindings;
- reconnect and revocation behavior.

### User-data assets

- clipboard content;
- files and metadata;
- notifications;
- media streams;
- screen/audio/camera data;
- device status and presence information;
- audit records where they contain sensitive metadata.

### Platform assets

- OS credentials and authentication state;
- privileged-service authority;
- driver/system-extension authority;
- system configuration;
- platform permission grants;
- local IPC endpoints.

## Actors and attacker classes

The threat model will distinguish actors by capability instead of treating all attackers as a single category.

### Legitimate actors

- owner;
- trusted device;
- temporarily authorized device/user where supported;
- local unprivileged Cross-Lab agent;
- privileged helper operating within its narrow contract;
- optional owner-operated relay or hub.

### Threat actors

- unauthenticated remote peer;
- network-path attacker able to observe, delay, replay, reorder, inject, or drop traffic;
- malicious or compromised paired device;
- compromised unprivileged Cross-Lab agent;
- compromised UI or plugin process;
- malicious local unprivileged process;
- compromised or malicious relay/hub;
- attacker with a lost or stolen device;
- malicious update repository/mirror;
- attacker attempting downgrade, replay, resource exhaustion, confused-deputy, or privilege-escalation attacks.

A fully compromised operating-system kernel, hypervisor, secure hardware, or owner root/recovery credential is generally outside the guarantee boundary of ordinary Cross-Lab operation. The threat model will state where such compromise invalidates guarantees rather than pretending Cross-Lab can defend against arbitrary platform-root compromise.

## Trust zones and boundaries

The security documents will use the following conceptual zones.

```text
External / Untrusted
    remote peer
    network path
    discovery metadata
    relay / signalling infrastructure
          |
          v
Network-facing Cross-Lab Agent
    transport adapter
    protocol parser
    authentication
    trust validation
    policy evaluation
    session/control orchestration
          |
          +----> normal user-space platform adapters
          |
          v
Authenticated Local IPC Boundary
          |
          v
Privileged Service / Helper
          |
          v
OS privileged APIs / drivers / system extensions
```

The recovery plane is not placed under ordinary trusted-device authority:

```text
Normal Device Trust --------X--------> revoked/lost device normal access

Recovery Authority ------------------> recovery command verifier
                                         |
                                         v
                                  permitted recovery action
```

Optional relays and hubs are connectivity infrastructure, not identity or authorization authorities. They must not possess Cross-Lab owner/device private keys or plaintext application payload authority merely because traffic traverses them.

## Mandatory security invariants

P0.2 will restate the following architecture requirements as testable security properties.

### Identity is transport-independent

IP addresses, MAC addresses, Bluetooth addresses, USB identity, QUIC identity, Iroh identity, libp2p PeerId, relay identity, and OS account names cannot by themselves establish Cross-Lab identity or trust.

### Authentication precedes trust and authorization

Sensitive operations require a cryptographically authenticated peer identity before trust and policy evaluation can grant authority.

### Trust is not authorization

A paired or trusted device receives no capability automatically. Policy is evaluated for the requested operation and context.

### Capability is not authorization

Advertising support for a capability only states that an operation can be performed. It does not grant another peer permission to invoke it.

### Control-plane authorization precedes data-plane use

A bulk/realtime data channel must be associated with a valid authorized operation/session context. Opening a data stream cannot bypass policy by skipping the control-plane decision.

### Privilege is revalidated locally

Remote authorization is necessary but insufficient for privileged execution. The privileged service authenticates its local caller, validates the requested privileged operation, checks the narrow operation contract, and rejects arbitrary/general execution interfaces.

### Privileged components are not network-facing peers

The UI, network listener, plugin runtime, and privileged helper remain separate. Remote peers communicate with the unprivileged agent; no remote peer obtains a direct privileged-service protocol endpoint.

### Recovery authority is independent

Normal trust revocation does not grant or derive recovery authority. Recovery commands are authenticated under a separate authority and limited to the recovery namespace supported by the platform.

### Security requirements are hard route filters

A route that does not satisfy required authentication, confidentiality, integrity, privacy, or policy constraints is ineligible regardless of performance.

### Third-party identifiers do not become domain authority

Concrete networking, UI, sync, FFI, and platform libraries remain implementation dependencies unless an approved ADR explicitly elevates a concept into the Cross-Lab domain model.

### Fail closed at authority boundaries

Unknown identity, malformed credential/protocol state, missing authorization context, expired authorization, failed privilege validation, unsupported capability, or ambiguous security state is rejected rather than implicitly permitted.

## Required threat categories

The threat model will analyze at least these categories for each applicable boundary:

- identity spoofing and credential substitution;
- pairing interception or unauthorized enrollment;
- replay of authentication/control/recovery operations;
- protocol downgrade and version-confusion attacks;
- tampering with capability advertisements or authorization context;
- confused-deputy behavior across agent/platform/privileged boundaries;
- unauthorized data-stream creation or stream substitution;
- stale authorization after revocation or policy change;
- malicious trusted peer behavior;
- privilege escalation through local IPC;
- relay/hub observation, modification, impersonation, or availability attacks;
- denial of service, unbounded queues, parser/resource exhaustion, and connection floods;
- sensitive-data leakage through logs, audit events, diagnostics, discovery, or presence;
- update freeze, rollback, repository compromise, and signing-role compromise;
- lost/stolen-device access and recovery abuse;
- plugin/UI compromise attempting to inherit authority;
- route changes or reconnects that accidentally weaken prior security assumptions.

The documents may use STRIDE terminology where it improves clarity, but Cross-Lab will not force every threat into a STRIDE table if a boundary/property-oriented description is clearer.

## Authorization flow

The normative conceptual flow is:

```text
receive untrusted request
        |
        v
parse with explicit bounds
        |
        v
authenticate peer identity
        |
        v
validate current trust / revocation state
        |
        v
validate advertised + local capability support
        |
        v
evaluate policy for operation + context
        |
        v
create bounded authorization context
        |
        +------> ordinary user-space operation
        |
        +------> authorized data-plane binding
        |
        +------> privileged IPC request
                     |
                     v
              local caller authentication
                     |
                     v
              privileged request validation
                     |
                     v
              narrowly permitted OS action
```

Every later implementation may optimize this flow, but it may not remove the logical checks represented by these boundaries.

## Compromised trusted-device model

Pairing does not turn a device into a universally trusted principal. A compromised paired device must be constrained by:

- per-capability policy;
- operation-level authorization;
- revocation;
- explicit privileged-operation boundaries;
- limited session scope;
- local platform permissions;
- auditability where appropriate;
- obligations such as owner confirmation or biometric approval when later specifications define them.

Cross-Lab therefore treats trust as membership/relationship information rather than blanket authority.

## Session, reconnect, and revocation properties

The P0.2 model will require later session specifications to ensure:

- a new transport connection cannot inherit identity solely from a previous connection;
- reconnect requires fresh authentication appropriate to the session design;
- session state cannot outlive revocation in a way that permits new sensitive operations;
- active sensitive operations react to revocation according to an explicit policy rather than unspecified behavior;
- authorization contexts have clear lifetime and scope;
- route changes cannot silently weaken authenticated peer or policy bindings;
- replayed control messages cannot recreate expired or revoked authority.

Exact nonces, transcripts, credential formats, and key schedules are intentionally deferred.

## Privileged-service boundary

The privileged-service model will require:

- local-only IPC;
- authenticated caller identity appropriate to each OS;
- narrowly typed operations rather than arbitrary command execution;
- request validation independent from the network-facing agent's checks;
- least privilege inside the helper itself;
- no general peer discovery, relay, transport, plugin, or UI responsibilities;
- no assumption that possession of an IPC endpoint automatically grants authority;
- audit events that avoid secrets and sensitive payload content.

Platform-specific mechanisms such as polkit, XPC, Windows services, launchd/systemd details, login providers, and driver interfaces are deferred to their platform milestones.

## Recovery boundary

The threat model will treat recovery as a separate authority and command namespace. It will analyze:

- stolen normal device credentials;
- stolen recovery credentials;
- replayed recovery commands;
- malicious normal peers attempting recovery actions;
- recovery commands after ordinary trust revocation;
- compromised relays delivering recovery traffic;
- visibility/audit requirements;
- platform limitations on locate, lock, wipe, credential rotation, and data recovery.

The model will not assume that every platform can implement every recovery action.

## Relay and hub assumptions

Owner-hosted infrastructure improves owner control but is not automatically trusted with plaintext or signing authority.

The initial model will assume a relay/hub may be unavailable, malicious, compromised, or able to observe network metadata. Later designs must minimize what such infrastructure can learn or authorize.

Mandatory Cross-Lab operation cannot depend on a Cross-Lab-operated cloud account or trusted central server.

## Audit and privacy

Auditability is required for sensitive actions, but audit logs are themselves sensitive assets. The model will require later designs to minimize logged payload data and protect identifiers, device-state information, presence, authentication attempts, and recovery activity from unnecessary disclosure.

Secrets, private keys, credentials, full clipboard contents, file contents, media payloads, and equivalent sensitive application data must never be included in normal logs.

## Availability and resource safety

Because Cross-Lab is network-facing and intended to remain lightweight, resource exhaustion is a security concern rather than only a performance concern.

Later implementations must use bounded parsing, bounded queues, explicit limits, cancellation, backpressure, connection/session limits where appropriate, and defensive behavior for unauthenticated peers. Exact thresholds are implementation decisions unless protocol interoperability requires them.

## Threat-to-control-to-test mapping

`security/THREAT-MODEL.md` will include a table or equivalent structured section where each material threat records:

```text
Threat ID
Asset / boundary
Attacker capability
Attack scenario
Required control
Verification or test obligation
Residual risk / deferred decision
```

This creates traceability from security reasoning to Phase 1 and later tests. It does not require tests for features that do not yet exist; it records the future obligation and identifies the milestone responsible for satisfying it.

## Security-boundary document

`docs/architecture/SECURITY-BOUNDARIES.md` will remain shorter and more normative than the threat model. It will define the development rules for:

- remote input entering the agent;
- identity/authentication boundary;
- trust/policy boundary;
- control/data-plane boundary;
- platform-adapter boundary;
- privileged local IPC boundary;
- recovery boundary;
- optional infrastructure boundary;
- update boundary.

A developer should be able to read this document and determine where validation and authority checks belong without reading the entire threat catalog.

## Verification of P0.2

P0.2 is successful when:

- every security invariant in the Master Architecture has a corresponding threat-model property;
- every authority-bearing process boundary has an explicit trust assumption;
- no transport/library identity is accidentally promoted to Cross-Lab identity;
- capability support and policy authority remain distinct;
- data-plane authorization cannot bypass the control plane;
- the privileged-service boundary requires independent local validation;
- recovery remains independent from normal trust;
- relay/hub infrastructure is not treated as an implicit authorization authority;
- replay, downgrade, resource exhaustion, revocation, compromised-peer, update, and privacy threats are represented;
- unresolved cryptographic/protocol questions remain clearly deferred instead of being silently decided;
- later Phase 0 and Phase 1 security-test obligations can be derived from the model.

## Non-goals

P0.2 will not:

- implement cryptography;
- select exact signature, KDF, AEAD, PAKE, handshake, certificate, or key-storage formats;
- define the final pairing transcript;
- define final protocol serialization;
- implement Rust crates;
- implement Quinn or any network transport;
- define OS-specific privileged IPC APIs;
- implement recovery or update mechanisms;
- threat-model every future capability in platform-specific detail;
- select the repository license.

## Follow-on milestones

The threat model is an input to, not a replacement for, the remaining Phase 0 specifications. At minimum, later work must refine:

- identity and key hierarchy;
- pairing and authenticated enrollment;
- trust, revocation, and rotation;
- policy and authorization semantics;
- protocol envelopes and compatibility;
- secure-session and transport contracts;
- recovery command authentication;
- update trust and rollback protection;
- Core Simulator security scenarios and negative tests.

Any later decision that conflicts with this design or the Master Architecture requires explicit review and, when material, an ADR.
