# P0.3 — Identity and Key Hierarchy

**Status:** Completed  
**Phase:** Phase 0 — Architecture and Security Specification

## Objective

Freeze the Cross-Lab owner/device identity hierarchy, stable identifiers, credential roles, epochs, rotation semantics, and private-key handling constraints required by the Core Simulator and later platform implementations.

## Scope

P0.3 defines domain identity independent from transports, operating-system accounts, and mutable device metadata. It separates owner root, device-signing, administrative, recovery, and per-device key roles and specifies how credentials and stable identifiers behave across rotation and revocation.

## Decisions and Constraints

- `OwnerId` and `DeviceId` are stable Cross-Lab identifiers and remain independent from transport addresses and ordinary key rotation.
- Key identifiers are distinct from stable owner/device identifiers.
- Owner root, device-signing, administrative, recovery, and device authentication authority are not collapsed into one reusable private key.
- Mutable capability, platform, connectivity, and presentation metadata are not identity authority.
- Private keys remain local and should use hardware-backed protection where practical.
- Public domain types remain independent from specific Rust cryptography crates.
- The concrete v1 cryptographic profile is governed by ADR-0002.

## Acceptance Criteria

The identity specification defines identifier semantics, credential/delegation fields, authority roles, issuance and rotation behavior, epoch handling, supersession/revocation interactions, malformed/stale credential failure behavior, and private-key isolation expectations.

## Verification

The specification was checked against the foundational threat model, transport-independence requirements, recovery separation, and the rule that third-party transport/library identifiers cannot become Cross-Lab identity authority.

No production cryptographic implementation or crate version was selected in this milestone.

## Handoff

P0.3 supplies the identity and authority model consumed by P0.4 pairing/trust/revocation, P0.6 canonical security transcripts, P0.7 session authentication, and Phase 1 identity implementation.
