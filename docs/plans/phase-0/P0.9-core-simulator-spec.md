# P0.9 — Core Simulator Specification and Phase 0 Review

**Status:** Completed  
**Phase:** Phase 0 — Architecture and Security Specification

## Objective

Freeze the initial Rust workspace boundaries, deterministic Core Simulator responsibilities, required positive and negative scenarios, and Phase 1 completion criteria before production implementation begins.

## Scope

P0.9 defines the smallest platform-independent environment that can prove Cross-Lab identity, pairing, trust, policy, protocol, logical sessions, control/events, operation-bound data streams, reconnect, revocation, cancellation, resource limits, and shutdown behavior.

## Deliverables

- `docs/architecture/CORE-SIMULATOR.md`
- `docs/adr/ADR-0006-crypto-crate-boundary.md`

## Dependencies and Governing References

- `docs/architecture/MASTER-ARCHITECTURE.md`
- all P0.2-P0.8 normative security, identity, trust, policy, protocol, session, recovery, update, audit, and plugin-boundary specifications

## Decisions and Constraints

- The simulator uses production domain cryptographic primitives; it does not use toy crypto for security semantics.
- The first transport is a deterministic in-memory harness and is not presented as production network security.
- The initial workspace contains only crates required by the Phase 1 domain/security contracts.
- GPUI, UniFFI, SQLite, Quinn, Iroh, libp2p, platform adapters, privileged helpers, plugin runtimes, sync/media dependencies, and updater dependencies are excluded from the initial simulator unless a concrete Phase 1 requirement changes that decision.
- Queues, frames, collections, operations, and task lifecycles are bounded and explicitly cancelable/shutdown-aware.
- Tests prove observable domain behavior and security properties rather than internal implementation details.
- The focused shared cryptographic implementation boundary is governed by ADR-0006.

## Acceptance Criteria

The simulator specification defines workspace responsibilities and dependency direction; deterministic node, clock, RNG, and transport test seams; required identity/pairing/session/policy/control/data-stream flows; malformed/replayed/unauthorized/revoked/resource-exhaustion scenarios; and the implementation sequence from repository foundation through Quinn networking.

## Verification

P0.9 was reviewed against the Master Architecture Phase 1 scenarios and foundation success criteria. The specification preserves platform independence, transport-independent identity, default-deny policy, operation-bound data streams, fresh reconnect authentication, revocation enforcement, bounded resources, and deterministic testing.

No Rust workspace or production implementation is created by P0.9 itself.

## Handoff

P0.9 closes milestone-level Phase 0 specification work and hands the project to the formal Phase 0 closeout gate. After that gate is satisfied, implementation begins with Phase 1 / M1 Repository Foundation on the `foundation` branch.
