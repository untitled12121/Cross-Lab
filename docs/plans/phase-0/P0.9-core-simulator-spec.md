# P0.9 Core Simulator Specification Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Freeze the Phase 1 Core Simulator architecture, crate responsibilities, deterministic scenarios, negative/security tests, and completion criteria before Rust workspace creation.

**Architecture:** The simulator composes `identity`, `policy`, `protocol`, and `core` domain crates with a deterministic in-memory transport harness. It proves owner/device credential semantics, pairing, trust, session authentication, capabilities, policy, control/events, operation-bound streams, disconnect/reconnect, revocation, cancellation, bounded queues, and shutdown without OS-specific code.

**Tech Stack:** Markdown specification. Phase 1 dependency versions are verified only after Phase 0 review/ADR approval.

**Spec:** Master Architecture Sections 36-46, 49-54 plus all P0.2-P0.8 specifications.

## Global Constraints

- The simulator must use production domain cryptographic primitives for identity/signatures/transcripts; no toy crypto.
- The in-memory transport is a deterministic test harness, not production network security.
- No GPUI, UniFFI, SQLite, Quinn, Iroh, libp2p, platform adapters, privileged helper, plugin runtime, sync/media dependencies, or updater is needed for the initial simulator.
- Tests must prove observable behavior and security invariants rather than internal implementation details.
- Queues/counts/frames are bounded and cancellation/shutdown are explicit.
