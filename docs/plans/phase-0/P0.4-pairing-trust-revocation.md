# P0.4 Pairing, Trust, and Revocation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Freeze the Phase 1 pairing bootstrap, authenticated pairing transcript, trust-record lifecycle, and revocation semantics.

**Architecture:** Pairing uses one-time high-entropy out-of-band bootstrap material to authenticate a canonical transcript without treating network proximity as trust. Device membership is created only after owner-authorized credential issuance and device proof of possession. Trust is explicit local state and revocation invalidates ordinary future authority.

**Tech Stack:** Markdown specifications and ADRs. No production code is added in P0.4.

**Spec:** `docs/architecture/MASTER-ARCHITECTURE.md` Sections 6-8, 12, 32, 42, 44 and `docs/architecture/IDENTITY-AND-KEYS.md`.

## Global Constraints

- Primary Phase 1 pairing must not rely on a short numeric secret.
- Discovery/proximity does not imply trust.
- Pairing must bind both device identities/keys, owner domain, protocol/profile, and fresh nonces into one canonical transcript.
- Pairing authorization must be explicit and replay-resistant.
- Partial pairing failure must not silently create ambient trust.
- Revoked devices cannot create new ordinary sessions/operations.
- Recovery authority remains separate.
