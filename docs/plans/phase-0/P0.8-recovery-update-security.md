# P0.8 — Recovery, Update Security, Audit, and Plugin Boundary

**Status:** Completed  
**Phase:** Phase 0 — Architecture and Security Specification

## Objective

Freeze the separate recovery authority, trusted update model, audit/privacy rules, and reserved plugin authority boundary before privileged services or extensibility are implemented.

## Scope

P0.8 defines recovery commands and authority separation, update metadata/signing roles, rollback/freeze protections, structured audit and redaction rules, and the security boundary future plugins must use. Runtime updater, recovery agents, privileged installers, and plugin runtimes remain later implementation work.

## Decisions and Constraints

- Recovery credentials are independent from ordinary device/session credentials.
- Recovery operations are narrow, target-bound, replay-resistant, visible/auditable, and platform-compliant.
- Recovery cannot silently restore ordinary trust or become a covert-surveillance bypass.
- Update distribution infrastructure is not signing authority.
- Production update trust separates metadata/signing roles and protects against rollback, freeze, mirror compromise, and key compromise.
- Platform vendor signing/notarization remains an additional requirement rather than a replacement for Cross-Lab update trust.
- Audit logs exclude secrets and sensitive payloads by default and apply structured redaction/minimization rules.
- Plugins do not inherit owner root authority, device private keys, arbitrary network access, unrestricted filesystem access, or privileged-service authority.
- The concrete v1 update trust profile is governed by ADR-0005.

## Acceptance Criteria

The recovery/update specification defines recovery authority, command namespace, replay protection, trust/revocation interaction, update roles, artifact authorization, rollback/freeze behavior, root rotation/compromise recovery, and privileged installation boundaries. Audit/privacy and plugin-security documents define the minimum information and authority that may cross those future boundaries.

## Verification

The milestone was reviewed against the threat model for recovery abuse, update repository compromise, rollback/freeze, privilege escalation, sensitive logging, and plugin/UI authority inheritance. No recovery, updater, plugin runtime, or privileged installer dependency was added.

## Handoff

P0.8 supplies security constraints that later recovery, updater, plugin, privileged-service, and release-engineering milestones must implement without weakening the core trust model.
