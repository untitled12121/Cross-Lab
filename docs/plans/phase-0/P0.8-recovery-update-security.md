# P0.8 Recovery and Update Security Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Freeze the separate recovery authority/command namespace and the TUF-style update trust/rollback/freeze model before privileged components exist.

**Architecture:** Recovery is independent from ordinary device trust and cannot silently restore ordinary membership. Update distribution is untrusted; trusted metadata/signing roles authorize artifacts independently from mirrors/network paths. Neither subsystem is implemented in Phase 1, but both constrain identity/protocol architecture now.

**Tech Stack:** Markdown specification and ADR. `tough` remains a future candidate dependency.

**Spec:** Master Architecture Sections 4.5, 29, 32, 33, 35, 42-44.

## Global Constraints

- Recovery keys are not ordinary device-signing/session keys.
- Recovery commands are narrow, target-bound, replay-resistant, visible/auditable, and platform-compliant.
- Recovery cannot become covert surveillance or an ordinary trust bypass.
- Update mirrors/servers are not signing authorities.
- Production update trust uses TUF-style role separation, signed metadata/artifacts, expiry/freeze and rollback protection, and compromise recovery.
- No updater/recovery runtime dependency is added in Phase 0/Phase 1.
