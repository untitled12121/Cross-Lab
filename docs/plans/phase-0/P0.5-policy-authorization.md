# P0.5 Policy and Authorization Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Freeze capability identifiers, default-deny policy semantics, contextual authorization, approval obligations, and operation-scoped authorization required by Phase 1.

**Architecture:** Capability support and permission remain separate. The destination evaluates a small deterministic policy model against locally validated context. Successful authorization creates a bounded operation context rather than ambient peer authority.

**Tech Stack:** Markdown specification. No production dependencies.

**Spec:** Master Architecture Sections 4, 7, 9, 10, 14, 37, 42, 44 and the P0.2/P0.4 security specifications.

## Global Constraints

- Default deny.
- Trust and capability advertisement never imply permission.
- Security-sensitive context must be locally derived or cryptographically verified.
- Interactive approvals are evidence-bearing obligations, not boolean peer claims.
- Authorization must bind source, destination, capability/operation, session, lifetime, and relevant trust/policy revisions.
- Phase 1 policy remains deliberately small; do not build a generic policy language.
